# TASK-012｜用户参与设计与自动头部交付链路核验

日期：2026-08-09  
性质：产品交互与技术路线核验；不替代 TASK-002 的实体供给核验、TASK-003 的需求验证或 TASK-004 的数字流程自测。  
状态：授权项 1 已开启；授权项 2 与 3 待杨授权。  
禁止：不开发正式网页或应用、不采购软件或积分、不联系供应商、不向客户收款、不把人工补救当作自动流程已成立。

## 一、已确认的产品方向

以下为杨的方向，属于 F-P 的产品设想，不是当前已实现能力：

1. 身体、底座和整体风格由 PPSB 设计并控制，用户在有限方案中选择；
2. 头部由照片生成初稿，用户在界面中参与设计和确认；
3. 用户不必具备专业设计能力，也不必从大量身份线索模板中逐项挑选；可通过在照片或预览画面上标记、涂画或短文字指出“这里不像”；
4. 用户确认预览并付款后，锁定该数字形象版本；
5. 对熟悉付款人的接收者而言，脸本身即是关系入口。基线产品不强制加入共同物件、文字或内部梗。此为产品定义边界，属 F-P 产品方向，不是待验需求假设。待验的是接收者是否愿意接受并摆放这一基线产品；共同关系线索不是预设必需品，只在基线失败后作为可选变体测试；
6. 目标交付链路应由软件和 AI 自动完成，不以人工沟通或人工改模作为常规客户流程。

“AI 可以做到几分像”“用户一定会满意”“预览与实物必然一致”均未被验证，不得写成能力事实。

## 二、要回答的问题

| 编号 | 待验问题 | 当前等级 |
| --- | --- | --- |
| H1 | 普通用户能否用照片与标记完成头部微调，而不需要专业设计语言 | H |
| H2 | 系统能否把用户的标记稳定转为可预览、可打印的头部修改 | H |
| H3 | 用户确认的屏幕三维预览能否与实体成品保持足以支撑交付的对应关系 | H |
| H4a | 屏幕预览与实体是否一致 | H |
| H4b | 预览与实体一致，但付款人拿到手后仍不想留，即产品形态本身的问题 | H |

H4a 与 H4b 是两种性质不同的失败，不得合并为“满意度落差”。H4a 指向交付与工艺，可由预览保真度与工艺改进修复；H4b 指向产品形态本身，工艺改进无法修复。

只有独立客户的付款是 F-M。它证明付款人愿为当时的报价与数字预览付款，不证明实体交付满意、接收者愿意摆放或长期留存。付费参与者的付款、样品与试用行为一律不得升级为 F-M。

## 三、目标流程与失败处理

目标流程为：上传照片，选择身体与底座，生成头部预览，标记或说明需调整处，系统更新预览，用户确认并付款，生成可打印文件，制造实体并交付。

目标商业流程不设人工客服代替系统理解用户标记。若系统无法理解，合格的产品行为只能是：请用户重新标记或补充说明，明确告知当前不支持，或让用户自行放弃本次提交。测试中出现人工改图、人工改模或人工解释时，必须单列为“当前自动化缺口”，不得记为流程成功。

## 四、核验设计

本任务先设计和测试一条最小交互链，不开发正式产品。每次测试固定记录：

| 环节 | 记录内容 |
| --- | --- |
| 初稿 | 输入照片；初稿是否被认为基本像；未被接受的具体位置 |
| 用户标记 | 在哪里标记；采用何种图示或文字；用户原话 |
| 系统解释 | 系统识别出的调整意图；是否要求用户重述 |
| 更新预览 | 实际改变了什么；用户是否确认；是否继续标记 |
| 数字版本锁定 | 锁定的预览、身体、底座与版本号；付款前后的修改规则 |
| 可打印性 | 三维文件的封闭性、壁厚、头身接口及打印前处理问题 |
| 实体对应 | 屏幕预览与实体在脸型、发型、眼镜等关键线索上的一致与落差 |
| 交付后 | 付款人对实体的满意或不满意及原因；与付款前确认分开记录；不满意须归类为指向工艺（H4a）或指向产品本身（H4b） |

不预设接受率、工时、相似度或预览实体落差的阈值。首批可比记录回来后，才由杨决定后续判据。

## 六、授权闸门与交付物

本任务分为三项独立授权，不自动连续：

1. 设计交互流程与记录表。已于 2026-08-09 开启。范围限内部：定义照片、初稿、标记、系统理解、更新预览、版本锁定、实体交付的完整数据链，并设计记录字段。本项不花钱，不对外发布。
   本项明确不做：不决定具体 UI 话术、标记类别与默认提示；不让第二波执行者接触任何自动工具；不开始数字工具测试；不做实体样品。

闸门理由：没有普通用户如何表达“不像”的原始语料，标记界面只能凭想象设计；若在日志锁定前让执行者接触自动工具，工具能力会反向塑造其设计方式，第二波的隔离随即失效。
